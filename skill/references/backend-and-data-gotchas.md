# Backend & data-layer gotchas: Server Actions, entities, Mentor process

Every entry below is a real bug or a real process failure, not a
hypothetical. The pattern across most of them: **a change that is locally
correct (0 validation errors, the screen it targets works) can still be
globally wrong**, because OutSystems has no compile-time link between a
Server Action's own logic and every other consumer of the same entity,
aggregate, or dependency. Say the dependency in words; verify every
consumer, not just the one you touched.

**If you're here because of a live bug, not a wave in progress:** check
`recipes.md` too — several of its recipes exist precisely because a bug
here was found during debugging, not planning.

## 1. `List mapTo { }` with zero explicit mappings zeroes EVERY field, not just the ones the mapping "forgot"

Converting an aggregate's record list (which may carry join columns) into a pure entity record list for a server action's input parameter is commonly done with `List mapTo { }` — and it is easy to leave that mapping block completely empty when the intent was "just pass the records through unchanged," especially when a prior version of the flow used the aggregate's list directly and a later refactor introduced the `mapTo` only to satisfy a type mismatch. An empty `mapTo { }` is not a no-op passthrough: it produces new records where **every single field is set to its type's default** (empty text, zero, false) — not just the fields a hurried mapping omitted. This was discovered after a "create new checklist version" flow (`PublishChecklistVersion`, wired from `ChecklistDetail`'s save action) silently wrote every `ChecklistItem` in every new version with `AnswerType = ""`, `Axis = ""`, `Guidance = ""`, etc., even though `Title` and `Code` were visibly correct elsewhere in the same UI (they came from a different display path, not this mapped list) — masking the defect for weeks, because the fields that were visibly correct gave false confidence that the mapping worked. The downstream damage was severe and delayed: an unrelated screen's `RadioButtonGroup`, gated by a `Visible` expression comparing `AnswerType = "Scale"`, rendered zero options for every item in every audit created after the flawed version was published — with 0 validation errors at every step, because nothing about an empty-string field is invalid. When a `mapTo` is used to pass an aggregate's list into an action expecting the plain entity type, list every field the target entity actually has, explicitly, even ones "the actual code path doesn't seem to touch" — an incomplete mapping is not caught by the compiler, by 0 validation errors, or by any screen that happens to display a different subset of fields than the ones actually broken.

**Verify after publish:** for any entity created via a non-trivial `mapTo`, read back a freshly created record's fields that the mapping was supposed to carry over (not just the ones the current screen displays) and compare against the source — an aggregate/DB read showing unexpected defaults (empty string, `0`, `false`) on a field that had a real value in the source is the signature of an incomplete `mapTo`, and it will not surface as an error anywhere near the mapping itself.

## 2. Two `AtStart` aggregates where one's filter reads the other's `.Current` have NO guaranteed execution order — and a working order can silently break when either aggregate's OML node is recreated

An aggregate `B` whose filter references `A.List.Current.<field>` (e.g., a detail screen's items aggregate filtering by the parent record's active-version id) appears to work reliably through many published revisions — `A` happens to execute before `B` because of how the two nodes were originally created and laid out in the flow, not because the platform guarantees it. This ordering is NOT a property the platform tracks or protects: it is incidental. The moment either aggregate's node is deleted and recreated — e.g. as a side effect of an unrelated fix elsewhere on the same screen, such as rewriting a `mapTo` block feeding a completely different action — the platform can lose track of the implicit dependency, and `B` may now fire before `A` has returned data. `B`'s filter then evaluates against `A`'s default/empty `.Current` (e.g. an identifier of `0`), returning zero rows — with 0 validation errors, because a filter against a default value is syntactically and semantically valid, just wrong at runtime. This was discovered as a regression introduced by an unrelated same-screen fix: a screen that had correctly shown 8 items through many prior revisions suddenly showed "0 itens" immediately after a `mapTo` rewrite on a different aggregate's downstream action, with the network call for the items aggregate still returning `200 OK` (not erroring — just silently empty). The fix is to never rely on implicit `AtStart`/`AtStart` ordering when one's filter depends on the other's `.Current`: set the dependent aggregate to `Fetch: OnDemand` and trigger its refresh explicitly from the source aggregate's own `OnAfterFetch` handler, so the sequence is enforced by wiring, not by incidental node order.

**Verify after any edit that touches an aggregate whose filter reads another aggregate's `.Current`** (even when the edit itself targets a different, seemingly unrelated node on the same screen): reload the screen fresh and confirm the dependent aggregate still returns its expected row count — a `200 OK` network response is not proof of correct data, and this class of regression produces no validation error anywhere.

## 3. Mentor can silently revert an unrelated prior fix while applying the one you asked for — re-verify every change on every turn, not just the one you just requested

Asking Mentor to fix a narrow, unrelated issue (e.g. two "Unused Attribute" warnings on a list-insert element) can cause it to also undo a *different*, already-applied, already-verified fix from an earlier turn in the same session — with no explicit warning that it did so. The only trace was a contradiction buried in that turn's own prose summary (describing the aggregate as "a join aggregate with no GroupBy" when the immediately preceding turn had added a GroupBy specifically to fix a duplication bug) — easy to miss unless the summary is read adversarially. Live verification after that turn confirmed the regression: the GroupBy was gone, duplicates were back. This is a distinct failure mode from "0 validation errors doesn't prove the fix worked" (lesson #5 below) — here the fix genuinely *had* worked, verified live, and a *later, unrelated* turn silently threw it away as a side effect. **The fix is procedural: treat every Mentor turn as capable of touching more than what you asked it to touch, and re-verify the specific thing an earlier turn fixed after every subsequent turn on the same screen/aggregate/action — not just once, and not just the thing the current prompt targeted.** When asking Mentor to confirm a specific prior state is preserved, ask it to state explicitly, in its own words, whether that specific thing is still true (as opposed to just describing what it changed this turn) — this surfaces contradictions like the one above instead of letting them hide inside an otherwise-plausible summary.

**Related, opposite-direction failure (see lesson #7 below):** a fix applied to one Server Action can leave an *identical* bug live in a second Server Action that calls the same lower-level dependency — not because Mentor reverted anything, but because nobody asked it to check the second caller. Both failure modes have the same countermeasure: after any fix, explicitly enumerate every other place the same state/dependency is touched, and check each one — don't stop at confirming the one thing you asked for.

## 4. A screen aggregate's `Distinct` property and the `Exists` function are both unavailable to Mentor's Model API — plan around them, don't request them

Two OutSystems aggregate capabilities that would naturally solve "filter to only rows that have at least one match in another table, without duplicating" are not usable when Mentor is editing via its Model API on a **screen** aggregate: the `Distinct` checkbox is not exposed on the aggregate interface the API exchanges with (Mentor reported this honestly rather than silently no-op'ing it), and the `Exists` function is rejected by the validator specifically inside screen aggregates (it does work inside **server action** aggregates — a real platform inconsistency, not a Mentor limitation). Both are worth knowing about *before* spending a turn asking for either, since Mentor will (correctly, safely) refuse and ask for direction rather than fake success — but that still costs a full poll cycle. When a screen dropdown/list needs "distinct rows after a join that could multiply them," the two paths that actually work through Mentor's tooling are: (a) `GroupBy` on the screen aggregate itself, grouping by every attribute the UI actually reads (calculated/derived attributes used only for display, like a concatenated label, must also be pulled inside the GroupBy context or dropped) — the one used successfully here; or (b) move the query into a **server action** where `Exists`/`Distinct` are both available, and have the screen consume that action's output instead of a local aggregate. Prefer (a) when the query is otherwise simple and screen-local; reach for (b) when the filter logic is complex enough that fighting the screen-aggregate's more restricted feature set costs more than writing a small server action.

## 5. A Mentor Studio "done" reply proves nothing about the published app — publish, reload fresh, read the real error, AND run the full suite before trusting a fix

A change Mentor Studio describes as applied lives in its own edit session until the operator explicitly publishes it — checking "did it work" against the running app (a fresh screenshot, a hard-reloaded tab) before publishing will show the old behavior every time, regardless of what the turn actually did. **Always publish before treating "still looks wrong" as evidence the fix failed** — this is the static-gate replacement for whatever a `context_*`-style programmatic check would have caught, and it is weaker precisely because it depends on the operator remembering to publish first (see DELTA.md § Static gate became manual).

A second, distinct trap: an OML change that Mentor Studio itself reports as clean can still fail the platform's own publish step (a real OutSystems build/publish error), which is a different signal from Mentor's own summary text — always read the actual publish result/error in ODC Studio, not just Mentor's chat reply, before concluding a turn "worked." When a publish does fail with a real platform error, retrying the exact same request from scratch (rather than avoiding whatever pattern looked suspicious) is a reasonable first move — the failure is sometimes a one-off generation glitch, not a systemic problem with the pattern used.

**The escalation worth stating on its own**: publish-then-verify is necessary but still not sufficient when the fix touches a shared code path. A fix can publish cleanly and survive a manual live reproduction of the exact flow that was broken — and still be an incomplete or actively regressive fix, because the manual check only exercised one flow among several that share the same dependency. In one case, a broad rewrite of a screen's initialization logic published clean, fixed the originally-reported symptom on manual check, and was only proven to have introduced a *worse* regression (a foreign-key violation on save, absent before the "fix") by running the project's full E2E suite — the manual repro path never touched the code path where the regression actually lived. **Manual verification of the reported symptom is not a substitute for running the full regression suite before trusting any fix that touches initialization, shared aggregates, or a dependency multiple flows call** — reserve "I manually checked it and it works" for narrow, single-flow fixes; anything touching shared plumbing needs the suite, and running more than the wave's own spec needs the same explicit go-ahead as firing Mentor does (see SKILL.md's test-scope rule).

## 6. When a broad rewrite regresses a previously-good, measured state, reverting to that state is often faster and safer than debugging the rewrite further

A "root cause" fix that replaces a chunk of logic wholesale (an `OnInitialize` sequence, an aggregate's fetch timing, a multi-step guard) is a different risk class from a narrow patch — see lesson #3's related note on checking every consumer, and lesson #5 on why "0 errors + one manual check" isn't enough to trust it. When such a rewrite is published and the full suite (or a broader manual check) shows it made things measurably *worse* than the state before it — not just "still has the original bug," but a new, different failure — the fastest path back to a working state is usually **not** another round of "investigate the rewrite more deeply." It's describing, precisely, the specific changes the regressive turn made (diffing against what you know the previous, better-measured revision did) and asking Mentor to revert exactly those changes, while explicitly preserving anything published in between that wasn't part of the regression. This requires having a concrete "last known good" reference point — a revision number plus its measured result (e.g., "revision 154: 6/44 E2E tests failing, all pre-existing/known") — not just a vague sense that "it used to work better." Keeping that reference point (in a log, in the conversation, in a wave's status notes) is what makes "should I keep debugging or should I revert" a fast decision instead of another open-ended investigation. Reverting is not giving up on finding the real root cause — the regressive rewrite's own diagnosis can still be correct about *what's* wrong; the revert just declines to trust its untested fix for that diagnosis in favor of one that measurably worked.

## 7. The same guard/fix must be replicated in every Server Action that calls the same lower-level dependency — fixing one caller and not its siblings looks like a fresh bug later

When a bug lives in a shared, lower-level piece (a low-level `UpdateX` extended action, a validation helper, a data-shape assumption) and is reached through more than one higher-level Server Action (e.g. a "save one row" action and a "save all rows in a batch" action that both ultimately call the same `UpdateX`), fixing the bug's *symptom* in the one Server Action where it was first noticed does not fix it in any sibling action that reaches the same lower-level call through a different path. This is easy to miss because the sibling action may not be exercised by whatever manual check or test proved the first fix worked — it resurfaces later, looking like a brand-new bug with an unrelated stack trace, when in fact it's the identical root cause, just reached from a different entry point. **Whenever a fix targets a bug inside or just above a shared, lower-level dependency, explicitly search for every other Server Action in the module that calls the same dependency** (grep the extended/low-level action's name across the module's actions) **before considering the fix complete**, and apply the identical guard/fix to each one found — don't wait for each sibling to fail on its own schedule and get "fixed" as if it were a new, unrelated defect.

**A write-path/read-path variant of the same gap is just as common and easy to miss in the opposite direction.** A business rule enforced correctly on the action that *decides what to persist* (e.g. an "open a new record" action that only creates child rows for currently-active parent items) can still be missing from a sibling aggregate that *decides what to display* for the same parent record — because the two live in different places (a Server Action vs. a screen aggregate) and nobody thinks to ask "does the display query apply the same filter as the write path did?" Confirmed here: `OpenAuditCase` correctly filtered child item-creation by `IsActive = True`, but the read-only aggregate populating the results screen for that same record filtered only by the parent-version id, not by `IsActive` — so a since-deactivated item still rendered (with no matching response ever created for it, since the write path had correctly skipped it), and because that item also happened to have an empty secondary field, it rendered with no answer widget at all, permanently blocking form completion. The fix is the same discipline as the sibling-action case: whenever a business-rule filter exists on a write path, explicitly check every read path that surfaces records governed by the same rule, not just other write paths.

## 8. A cascading fallback ("try A, else B, else C") modeled as one `OR`-combined aggregate filter does not behave like sequential tries — and a `MaxRecords=1` "pick any matching row" query without `ORDER BY` is non-deterministic the moment more than one row can match

Two distinct bugs, same root mistake, found back-to-back debugging one fallback query (resolving which `ProtocolVersion` to use: prefer the one linked to the `AuditCase`, else the one linked to the `SourceRecord`, else any currently-active one).

**Bug A — `OR` across independent conditions in one aggregate does not short-circuit like `if/elseif/else`.** A single `WHERE` built as `(AuditCase.FK <> Null AND Join.Id = AuditCase.FK) OR (SourceRecord.FK <> Null AND Join.Id = SourceRecord.FK) OR (IsActive = True)` is evaluated as ONE boolean predicate per row, not as three sequential attempts. If `AuditCase.FK` holds a stale/orphaned id (pointing at a row that no longer exists, e.g. left over from before a related fix), the first branch's null-check passes (`<> Null` is true) but the join to that specific id matches zero rows — and because the whole expression is one predicate, no row anywhere satisfies branch 1 for that case, and the query returns **zero rows total**, never falling through to try branch 2 or 3 for that record. This is invisible from the OML/flow structure alone — it looks like a normal aggregate with a filter — and only shows up when a real orphaned FK exists, which won't happen on the happy-path data used while building the feature. **The fix: model "try A, else B, else C" as three separate, sequential aggregates (or a single aggregate re-executed with `SetParameters`), each with its own existence check on the specific candidate — not one combined filter.** Each level should independently confirm its candidate row actually exists before accepting it, then fall through to the next level's own query only if it doesn't.

**Bug B — `MaxRecords=1` with no `ORDER BY` picks an arbitrary matching row, and the ambiguity is invisible until more than one row can legitimately match at once.** The fallback's last resort ("any row with `IsActive = True`") assumed at most one candidate — but the actual data model allows *several* simultaneously (each parent record, e.g. each `Protocol`, can have its own independently-active version — a legitimate one-active-per-parent design, not a bug). With several `IsActive = True` rows present and no `ORDER BY`, the aggregate returned a real row — just not the one the tester had just created and populated; several of the other `IsActive = True` rows had an empty derived/indexed field, so the "successfully found something" path silently produced empty content anyway. This was masked twice: first because the field being read (`IndexedText`) is itself populated by a SEPARATE manual step (see the architecture-recipe entry on multi-step content pipelines) not run yet on the freshly-created row, and second because there was no error anywhere — a query returning *a* row when several exist is not a validation failure.

**The actual root cause behind both, worth naming explicitly:** neither bug was caught during design because the ambiguity space wasn't enumerated *before* writing the query — "how many rows can simultaneously satisfy this filter in real data, not just in the one scenario being tested right now?" was never asked. Both bugs were found the same way: fix, test against exactly one scenario, declare done, then the *next* real-data variation (an orphaned FK; a second active row) broke it again. This produces the appearance of "a new bug every time something is touched," when it's really the same unasked question surfacing once per untested data shape.

**Prompt block — for any query resolving ambiguity among several possible candidate rows:**
```
Before writing "<candidate-resolution query>", enumerate explicitly:
(1) how many rows can satisfy each filter level SIMULTANEOUSLY in real
data (not just the scenario being tested right now) — if the answer can
be "more than one," the query NEEDS a deterministic ORDER BY, never rely
on MaxRecords=1 alone;
(2) whether any FK used as "level 1" can point at a record that no
longer exists (orphaned) — if so, each fallback level must be a
separate query with its own existence check (Count > 0), NEVER a single
aggregate with OR combining the levels, because a branch that is "true
but has no match" zeroes the entire result, including the other
branches.
```

**Verify after publish:** test the fallback against every ambiguous data shape it's meant to handle, not just the primary scenario — an orphaned FK (level 1's target id changed or was deleted), and (when the design allows it) more than one row simultaneously satisfying the last-resort condition. A fix verified against only one freshly-created, cleanly-linked record proves nothing about the fallback logic itself.

## 9. Client-side polling in ODC Reactive Web needs plain JS (no native Timer widget exists) — and anchoring its state to a conditionally-visible container silently kills it

**ODC Reactive Web has no `Timer` widget.** That widget is a Traditional Web-only concept, which ODC does not support at all. A recurring "poll a server action every N seconds until a background process finishes" requirement (e.g. showing live progress of an AI analysis running server-side) has to be built with plain client-side JS — a recursive `setTimeout`/`setInterval` calling a client action — there is no declarative alternative to reach for. Don't spend a round asking Mentor to "use the native Timer" for this; confirm the platform lacks one before proposing a fix (Mentor itself may not volunteer this and will initially claim to have wired a "Timer" that is actually JS).

**The trap that breaks that JS polling loop, silently:** if the polling logic (or the JS `setTimeout`'s scheduling of its own next tick) is scoped to, or defined within, a container whose `Visible` is bound to a variable that changes during the poll (e.g. an "analyzing..." banner shown only while `IsAnalisando = True`), OutSystems Reactive can **unmount and remount that container** on that variable's change — destroying the JS execution context, including any captured reference to `$actions`, before the next tick can fire. Symptom: the very first poll tick works, the progress banner appears, and then it never updates again — no JS error, no server error, just silence. The Timer's `Enabled`/`Interval` (if a shim exists) can be perfectly configured and still not save you, because the container holding the visual state is exactly the thing getting torn down.

**The fix:** capture whatever the poll loop needs (a reference to the client action to call, e.g. `window._pollFn = $actions.PollingTick`) into a `window`-scoped variable **synchronously**, at the moment the poll is first triggered — before any `RefreshData` or state change that could cause a re-render — and have every subsequent tick call that captured `window` reference, never `$actions` directly from inside a callback that runs after a render cycle. Verify live (see backend-and-data-gotchas #5's own lesson: a clean publish and "0 errors" prove nothing) by watching the actual network tab in a real browser session for several polling intervals — a single successful poll call is not evidence the loop recurs; count how many calls actually fire.

## 10. A screen aggregate's `OnAfterFetch` binding can be silently missing or pointed at the wrong action — the aggregate fetching successfully proves nothing about whether anything reacts to it

A screen can `RefreshData` an aggregate on a timer/poll and get a `200` back every time (visible in network requests), while the screen never visibly updates, because the aggregate's `OnAfterFetch` event either isn't bound to any action at all, or is bound to a *different* action than the one that actually updates the local variables the UI reads. This is invisible from the request log — the fetch genuinely succeeds — and invisible from a Mentor "0 errors, applied" claim, because an unbound or mis-bound event isn't a validation error. Confirmed twice in the same debugging session: first the binding was simply absent, then — after a fix that was claimed complete — it turned out to still be pointed at a generic/wrong action name.

**Before concluding "the fetch works but the UI doesn't update" is a data or timing problem, verify the wiring explicitly:** ask Mentor (or inspect the OML) exactly what `<Aggregate>.OnAfterFetch` currently points to, by name — don't accept "it's wired up" as an answer; get the actual destination action name back and confirm it matches the action that assigns the screen variables the UI binds to.

## 11. `BinaryData` fields can corrupt for real-sized files on the ODC persistence round-trip — a tiny test fixture will never reproduce it

A `BinaryData` entity attribute (e.g. an uploaded PDF stored on `Document.File`) can come back corrupted when re-read from the database for a real-sized file, while a small file through the exact same write→read path works every time. Confirmed here with a 47597-byte PDF: every attempt to re-parse it after persistence (`GetDocument` → pass `.File` into an external-library PDF reader) failed with `iText.IO.Exceptions.IOException: PDF header not found`, across many consecutive publishes and multiple fresh re-uploads — while a 506-byte PDF through the identical entity/action never failed once. This was not a corrupt source file (verified independently with a local `file` command) and not an application logic bug in the traditional sense — it is a platform-level limitation in how ODC's `BinaryData` round-trips larger payloads through storage.

**The fix that actually worked: never re-read the persisted binary at all.** Extract/process whatever the binary is needed for (here: PDF text via an external C# library) **at upload time**, inside the same Server Action that receives the raw bytes from the client — while they're still intact in server request memory, before any `Create`/`Update` on the entity. Store the *extracted result* (plain text, in this case) on its own entity attribute, and have every downstream consumer (here: an AI-analysis batch action) read that pre-extracted field exclusively. Any code path that still re-reads `<Entity>.<BinaryAttribute>` after the initial write — even a "legacy" one that looks unreachable — will intermittently resurrect this exact failure the moment it runs against a real file; grep for every consumer of the raw binary attribute, not just the one in the original bug report (see lesson #7's same discipline, applied to a platform bug instead of an app bug).

**Verify after publish:** exercise the flow with a file at real/representative size, not a minimal fixture — see the fixture-size trap below, which is the reason this bug went undetected for a long stretch of a project's history despite a passing E2E suite.

## 12. A test fixture chosen for minimal size ("smallest file that satisfies validation") can systematically mask a size-dependent platform bug

An E2E binary-upload fixture (`tests/files/test-document-valid.pdf`) was 506 bytes — small enough to be a fast, convenient stub, and large enough to pass every content-type/extension check the app enforces. It passed the same upload-and-process flow on every run, before and after lesson #11's corruption bug was fixed, giving false confidence that the flow was healthy. The bug only ever reproduced with a real-sized file (47597 bytes) manually attached through the browser — the automated suite never once caught it, because "small enough to be convenient" and "small enough to dodge the corruption threshold" turned out to be the same fixture.

**The fix:** for any E2E fixture representing a binary upload (PDF, image, any `BinaryData`-backed attribute), use a file at a size representative of real usage, not the minimum that satisfies format/extension validation. Concretely, the fixture file was replaced in place with a real 47597-byte PDF, keeping the same filename so no test code needed to change — the existing assertions (filename, success toast) still hold, but the test now exercises the actual corruption-prone code path from lesson #11 as a permanent regression guard.

**Verify when adding or reviewing any binary-upload E2E fixture:** ask what size the fixture actually is and why — if the answer is "whatever was smallest/fastest to hand-craft," treat that as a coverage gap, not a convenience, for any flow where lesson #11's class of bug could exist.

## 13. A fix scoped too broadly on a shared action can regress a sibling flow that shares the same trigger condition but not the same requirement

A guard added to a shared Server Action (`AttachDocument`, handling document upload for more than one document `Kind`) checked only "is a binary file present," to decide whether to run PDF-specific extraction logic (lesson #11's upload-time fix). This condition is true for every file-type upload, not just the one document type (`SourceDocument`) the PDF logic was actually meant for — so a `Transcript` upload (a different `Kind`, also capable of carrying a file) started running PDF text extraction against a non-PDF/differently-shaped payload, crashing with the same `PDF header not found` error the original fix had just eliminated, now from a different call site. This is the inverse of lesson #7 (a guard *missing* from a sibling caller): here the guard was *present* but not discriminating enough, and applied inside a single shared action rather than being missing from one of several callers.

**The fix:** when adding type-specific logic gated on a condition inside an action shared by multiple types/flows (`File <> NullBinary()`), add the actual type/kind discriminator to the guard explicitly (`... AND Kind = Entities.DocumentKind.SourceDocument`), not just presence-of-data. **Verify after publish:** exercise every sibling flow that shares the same entry condition (every document `Kind` this action accepts, not just the one being fixed) in the same test pass — a fix confirmed only against the originally-reported flow will not surface a sibling regression like this until a user hits it days later on an unrelated-looking path.

## 14. An entity without `UpdateBehavior = Full` can silently drop a field the Server Action logic clearly assigns

An entity's Update action has an `UpdateBehavior` setting — the default in some scenarios is an optimized mode that only persists attributes the platform's own change-tracking considers "touched," rather than every attribute the record structure carries. A Server Action can build the record, explicitly assign a field (e.g. `AuditCaseRecord.Status = Finalized`), call `UpdateAuditCase`, get `0 errors`, and the write can still not land for that specific field in certain runtime scenarios — confirmed here by comparing the same entity's two attributes after the same action ran: one attribute (`SourceRecord.Status`, on an entity with default/Full update behavior) persisted correctly to `Finalized`; the sibling attribute (`AuditCase.Status`, on an entity that turned out to be configured with the optimized/partial mode) stayed at its old value, with no error, no warning, and a success toast from the calling flow. This produced a confusing three-part symptom on the UI side: the terminal status was reachable on one entity but not the other referencing the same business event, so any screen logic branching on the *wrong* one of the two status fields looked broken for reasons that had nothing to do with that screen's own code.

**The fix:** when a field is assigned in code but doesn't show up after a successful-looking Update, check the entity's `UpdateBehavior` property before suspecting the Server Action logic — set it to persist **all fields**, not just ones the platform decides were "changed." This is easy to miss because everything about the request/response cycle looks correct: `0 errors`, a normal publish, a normal success message from the flow.

**Verify after publish:** for any entity whose Update path is suspected of dropping a field, don't just re-read that one field — compare it against a sibling entity/field that's part of the same logical transaction (e.g. two status fields meant to reach a terminal value together) and confirm both actually reached the expected value on a fresh write, not just the one the original bug report happened to mention.
